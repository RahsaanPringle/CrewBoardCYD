CrewBoard · Planning guide

Reach CrewBoard by a memorable local network name

A practical implementation path for PBI-2: decide how the name is configured, announce it safely on the local network, preserve the IP-address fallback, and prove the behavior on real clients.

Source: PBI-2 Status: Implemented; hardware acceptance pending Scope: ESP32 CYD firmware + setup documentation

Implementation checkpoint

The firmware now validates an optional hostname, defaults to crewboard-cyd, sets it before enabling station mode, and starts the bundled mDNS/NetBIOS services after HTTP startup on a connected station with an IP. Name-service failures are logged and do not prevent HTTP startup. Setup AP mode stays IP-only. The display has dedicated Host, IP, and Network lines and retains seven status lines.

Hostname changes take effect after reboot. Reloading configuration during a staff-login save does not change the active hostname or restart discovery.

Verified in development: unchanged baseline and hostname-enabled firmware compile with ESP32 core 3.3.12; the full Node suite passes 65 tests without skips, including native C++ tests of the extracted production configuration/network-startup logic. Separate native form/hostname validation assertions also pass.

The native harness covers invalid/missing/empty/wrong-type names, the 15-character boundary, embedded NUL rejection, lowercase normalization, reboot-only changes, call ordering, the 20-second timeout, AP fallback, zero-IP guards, mDNS startup/service failures, and NetBIOS failure. It uses the installed ArduinoJson headers and fake networking APIs: it does not prove real network resolution or HTTP behavior on the physical device.

Recorded explicit build: ESP32 Dev Module, CPU 240 MHz, flash 80 MHz/QIO/4 MB, default SPIFFS partition scheme, and upload option 115200. Result: 1,096,238 bytes of flash (83%) and 52,684 bytes of globals (16%). Active TFT_eSPI setup: ILI9341_2, MISO 12, MOSI 13, SCLK 14, CS 15, DC 2, RST -1. These local settings must still be checked against the actual board revision.

1. What “done” should feel like

A crew member on the same supported local network can visit a memorable address such as http://crewboard-cyd.local/ instead of looking up an IP. The display still shows the IP, the existing HTTP server remains available by IP, and failure to start name advertisement never prevents CrewBoard from serving.

Reliable path

The IP address remains the always-documented fallback. mDNS and NetBIOS are best-effort conveniences, not dependencies for HTTP startup.

One configured identity

DHCP hostname, mDNS name, NetBIOS name, and the status display all derive from one validated hostname.

Honest expectations

.local requires a client/network that supports mDNS. A plain name such as http://crewboard-cyd/ depends on router or client behavior and is not guaranteed.

Not a DNS feature: the CYD will not run a DNS server, configure the router, or make local names work across guest networks, VLANs, or isolated Wi-Fi clients.

2. Where the feature fits today

The current boot path is concentrated in CrewBoard_CYD.ino: loadConfiguration() reads the SD-card configuration, connectToNetwork() joins station Wi-Fi or starts the setup access point, and setup() starts the HTTP server. The status display currently has a dedicated IP line and a network-name line.

  1. Configuration is loaded from /config.json on the SD card. Existing Wi-Fi, AP, and account settings are already checked at startup.
  2. The firmware sets WIFI_STA, calls WiFi.begin(), and waits up to 20 seconds.
  3. On success, it records WiFi.localIP(). On failure, it starts the setup AP and records WiFi.softAPIP().
  4. The HTTP server starts after either network mode is ready. Both modes are currently reached using the displayed IP address.

Configuration examples are in the SD-card sample. User-facing access and setup instructions live in the CYD README. There is no firmware build/test command in the root package scripts; the documented Arduino IDE/ESP32 board configuration is the current build path.

Keep the change focused: this PBI changes firmware configuration, network startup, status reporting, and setup docs. It does not need to change the browser app, API routes, authentication, or WebDAV.

3. Resolve these design questions first

Question Recommended starting decision Why / verify
What is the default? crewboard-cyd, documented and used for absent, empty, or invalid values. It is readable, unique enough for a small deployment, and within the 15-character limit. Warn through the existing log/display mechanism when falling back because a supplied value is invalid.
How should names be normalized? Accept ASCII letters, digits, and internal hyphens; normalize once to lowercase after validation. Lowercase gives every advertisement and display a consistent form. Never silently remove invalid characters and accidentally turn one name into another.
Which interface gets name services? Start mDNS and NetBIOS only after successful station Wi-Fi connection. Keep setup AP mode IP-only initially. The PBI requires the AP address and instructions to continue working, not hostname resolution there. Explicitly document this boundary; revisit AP announcements only if there is a concrete use case.
Which NetBIOS implementation? Use the NetBIOS library bundled with the inspected ESP32 Arduino core 3.3.12: #include <NetBIOS.h> and NBNS.begin(name). The installed header and source confirm the API. No additional library is needed on this version; compilation and Windows/network testing are still required.
Where is the sample config canonical? Add the optional setting to CrewBoard_CYD/sd-card/config.sample.json; check whether another shipped sample is meant to mirror it. Only the SD-card sample is directly called out in the firmware setup flow. Keep any maintained copies consistent if repository conventions require it.

4. Work in small, verifiable phases

Phase A · Confirm platform APIs

Check the actual ESP32 toolchain before implementation

  • Record the ESP32 Arduino core version and compile target used for the README’s ESP32 Dev Module configuration.
  • Confirm that WiFi.setHostname() is supported and determine the required call order relative to WiFi.mode() and WiFi.begin().
  • Confirm the bundled ESPmDNS API and how to advertise HTTP as http/tcp on port 80.
  • Find and verify the NetBIOS name service implementation for this core. Check name-length rules, start/failure behavior, maintenance, and any dependency/license implications.
  • Choose how to make firmware compilation repeatable or record the exact manual IDE steps and board-package version used for verification.

Exit check: all APIs have verified signatures and a known build environment; no speculative library calls remain.

What “platform APIs” means

The platform is the Espressif ESP32 board package installed through Arduino Boards Manager. It supplies the networking libraries alongside the compiler and board definitions. An API is the function your sketch calls into those libraries. Phase A answers three questions: does the function exist in our version, when can we call it, and how do we tell whether it worked?

Mechanism Plain-English job What it does not do
DHCP hostname Tell the router “my name is crewboard-cyd” while joining Wi-Fi. A compatible router may publish that name in its DNS. Setting the name alone does not guarantee that a browser can resolve the bare name.
mDNS Answer local multicast queries for crewboard-cyd.local. Advertise the HTTP service separately so discovery clients can find its port. It does not replace the HTTP server or work automatically across isolated networks.
NetBIOS / NBNS Answer supported Windows-style short-name queries using UDP port 137. It is not a Windows file-sharing server, and modern client policy may disable this name-resolution mechanism.

Local inspection results — November 6, 2026

These are development-machine findings, not proof of which firmware is flashed on the CYD. The Arduino IDE board/core selection and a compile must still be confirmed.

  • Installed board package: esp32:esp32 version 3.3.12. Documented board target: esp32:esp32:esp32 (ESP32 Dev Module).
  • Installed project libraries: ArduinoJson 7.4.3 and TFT_eSPI 2.5.43.
  • DHCP API: bool WiFi.setHostname(const char *hostname) exists. In this core it stores the default name; enabling station mode applies that stored name to the station interface. Set it before WiFi.mode(WIFI_STA), not merely before WiFi.begin().
  • mDNS APIs: MDNS.begin(name) and MDNS.addService("http", "tcp", 80) both return bool. Check each result separately. Supply the host label without .local; that suffix belongs in the browser URL.
  • NetBIOS API: the bundled NetBIOS.h exposes the global NBNS object and bool NBNS.begin(const char *name). It listens asynchronously, so its bundled example does not call an update method in loop().
  • NetBIOS detail: the implementation uppercases the name internally and returns whether it could listen on UDP 137. Keep a single lowercase application hostname and let the protocol handle its own representation. Startup success is not proof that every Windows client can resolve it.
Important lifecycle detail: loadConfiguration() also runs after staff-account changes. Do not accidentally reconfigure network naming or restart discovery whenever a login is saved. Prefer an explicit “hostname changes take effect after restart” policy and keep the active network identity consistent until that restart.

Phase B · Configure and validate the name

Make legacy configuration safe by default

  • Add an optional top-level hostname key to the SD-card sample, with a commented or documented example value of crewboard-cyd.
  • Implement a small firmware validator: 1–15 ASCII characters; first and last characters alphanumeric; interior characters alphanumeric or hyphen.
  • Use one default when the property is missing, empty, or invalid. Continue booting, and log the invalid-supplied-value fallback rather than silently accepting a modified name.
  • Normalize the accepted/default value once, store it in a dedicated String, and use that value everywhere. Do not make hostname validity a reason for otherwise valid configuration to fail.
  • Check edge cases: one-character name; 15-character name; leading/trailing hyphen; underscore; space; non-ASCII; empty; missing; JSON value of the wrong type.
{
  "wifi": {
    "ssid": "YOUR_WIFI_NAME",
    "password": "YOUR_WIFI_PASSWORD"
  },
  "hostname": "crewboard-cyd",
  "setupAccessPoint": {
    "ssid": "CrewBoard-Setup",
    "password": "CHANGE_THIS_SETUP_PASSWORD"
  }
}

Illustrative excerpt only. Preserve all existing configuration sections and never replace a real populated config.json with a sample.

bool validHostname(const char* value) {
  if (!value) return false;
  const size_t length = strlen(value);
  if (length == 0 || length > 15) return false;

  for (size_t i = 0; i < length; ++i) {
    const char c = value[i];
    const bool alphanumeric =
      (c >= 'A' && c <= 'Z') ||
      (c >= 'a' && c <= 'z') ||
      (c >= '0' && c <= '9');
    const bool internalHyphen = c == '-' && i > 0 && i + 1 < length;
    if (!alphanumeric && !internalHyphen) return false;
  }
  return true;
}

The validator can be a small helper in the firmware or a nearby header; keep it easy to test and avoid allocating transformed strings during character checks.

Phase C · Add best-effort station announcements

Keep IP access independent from name-service startup

  • Set the Wi-Fi station hostname before beginning the station connection, following the API ordering verified in Phase A.
  • After station Wi-Fi is connected and has a local IP, start mDNS with the normalized host label and advertise HTTP/TCP on port 80.
  • Start the verified NetBIOS name service on the station interface using the same normalized name.
  • Handle each start failure explicitly: log it via logEvent(), keep the HTTP server running, and do not claim that name access is available when it is not.
  • Do not start station mDNS/NetBIOS after the firmware falls back to WIFI_AP unless AP behavior is separately designed and tested. Keep http://192.168.4.1/ (or the displayed AP address) intact.
  • Confirm startup happens only once and that the server remains bound/available on the same interface as before.
// Illustrative station-only flow; verify exact APIs against the selected core.
if (!WiFi.setHostname(hostname.c_str())) {
  logEvent("Wi-Fi hostname setup failed");
}
// Enable station mode only after storing the hostname.
if (!WiFi.mode(WIFI_STA)) {
  logEvent("Station mode startup failed");
  // Follow the existing network failure/AP fallback path.
} else {
  WiFi.begin(wifiSsid.c_str(), wifiPassword.c_str());
}

// After WL_CONNECTED and a valid local IP:
if (!MDNS.begin(hostname.c_str())) {
  logEvent("mDNS startup failed; use IP address");
} else if (!MDNS.addService("http", "tcp", serverPort)) {
  logEvent("mDNS HTTP service failed; use IP address");
}

The installed core's verified NetBIOS start call is NBNS.begin(hostname.c_str()); check its boolean result and log failure independently of mDNS. Treat HTTP service-registration failure as a visible failure even if mDNS hostname startup itself succeeded.

Phase D · Show both useful addresses

Preserve the display’s existing status and log space

  • Display the normalized hostname as well as the current IP, including in AP fallback mode.
  • Keep the configured Wi-Fi SSID and existing startup/status log lines visible; adjust row spacing or label lengths intentionally rather than overwriting status text.
  • Use accurate wording for AP mode: it is still the hostname selected for the device, but name-based access may not be advertised there.
  • Inspect the physical 320×240 display at the configured rotation for clipping and overlap, including long legal hostnames and IPv4 addresses.

Phase E · Document, build, and prove it

Close the loop with real clients and a fallback path

  • Update the CYD README with the sample setting, validation/default behavior, .local URL, plain-name caveat, DHCP-reservation recommendation, and client/network limitations.
  • Document AP mode as IP-first/IP-only for this release, if the recommended scope is kept.
  • Build the documented firmware target with the recorded ESP32 core version, and run existing Node tests/checks to catch unrelated regressions.
  • Test on hardware: station DHCP hostname; mDNS HTTP service; IP URL; supported .local client; a Windows client for NBNS; no-Wi-Fi setup AP fallback.
  • Record tested board/core versions and client/ router combinations. Do not generalize a passing combination into a guarantee for every phone or router.

5. Runtime sequence

The ordering is important: the DHCP name must be set before station association, while service discovery waits until the station has an address.

flowchart TD A[Boot and read SD config] --> B{Hostname valid?} B -- yes --> C[Normalize and keep hostname] B -- absent, empty, or invalid --> D[Use documented default; log invalid supplied value] C --> E[Set station hostname before WiFi.begin] D --> E E --> F{Station joins within timeout?} F -- yes --> G[Record station IP] G --> H[Start mDNS and advertise HTTP TCP 80] H --> I[Start verified NetBIOS name service] I --> J[Start HTTP server; IP always works] H -. failure: log and continue .-> J I -. failure: log and continue .-> J F -- no --> K[Start setup AP] K --> L[Show AP IP; retain existing setup instructions] L --> M[Start HTTP server by AP IP]
Text alternative to the diagram

Load and validate config, set the DHCP hostname, then try station Wi-Fi. After a station IP is available, start mDNS and NBNS, then start HTTP regardless of advertisement success. If station Wi-Fi times out, start the existing setup AP and serve by its IP.

8. Risks and guardrails

Unverified NBNS package

Risk: an assumed header/API does not build for the documented ESP32 core, or introduces an unmaintained dependency.

Guardrail: verify the actual core/package, version, API, memory use, and license before choosing the integration.

Network name collisions

Risk: two devices advertise the same hostname on one LAN.

Guardrail: document choosing a unique hostname per CYD; keep the DHCP reservation advice and test collision behavior where feasible.

Display space

Risk: adding the hostname clips IP/network information or crowds startup logs.

Guardrail: measure layout on the physical display in both network modes and for the maximum accepted hostname.

Misleading plain-name promise

Risk: users expect every phone/router to resolve a bare hostname.

Guardrail: call it router/client dependent; explain this is not a DNS server and keep the IP as the fallback.

9. Pull-request completion checklist

  • Hostname validation and fallback behavior are implemented and covered by repeatable tests or an explicit hardware checklist.
  • DHCP hostname is set at the verified point before station association.
  • mDNS publishes HTTP/TCP port 80 only after the station has an IP.
  • NetBIOS uses an implementation verified to build with the target ESP32 core.
  • Each service failure is visible and non-fatal; HTTP by IP remains available.
  • Setup-AP behavior is unchanged and its hostname-resolution scope is documented.
  • Display shows hostname, IP, network, and existing status without overlap.
  • README explains tested `.local` support, DHCP reservation, plain-name caveat, and network/client limitations.
  • Firmware build result and tested hardware/client combinations are recorded in the PR.
  • Existing app behavior and security boundaries (HTTP authentication, API, WebDAV) are unchanged.
