A small-business server on a CYD?

CrewBoard already points toward a useful local server. Could the same kind of low-cost box host a simple intranet for a small team—more like a trimmed-down SharePoint than a full office platform?

The shape of the idea

Think of the CYD as a quiet little server on the business Wi-Fi. A phone, tablet, or office computer opens one home page and finds a few practical tools: shared files, notices, schedules, procedures, and links. The CYD display can show its name and network status; the browser does the real work.

The goal would be dependable basics for a small crew, without asking the owner to learn server administration. Keep it local-first, make setup understandable, and let a person copy the SD card to make a backup. The product idea is a private business server: it sits on the business's existing router, is intended for people on that network, and uses individual logins.

Scope note: This page is a concept sketch only. It does not change CrewBoard or propose a firmware implementation yet.

Storage: start with 32 GB, offer room to grow

For a first product, assume a 32 GB microSD card. Set aside about 2 GB for the server software and bundled apps, and advertise the device as a 20 GB server for shared business files. The remaining space is a cushion for filesystem overhead, updates, and reliable operation; the advertised capacity is a simple promise, not a claim that every byte on the card is customer storage.

This gives a small business ample room for printable forms, policies, and everyday documents without making a terabyte card a requirement. If a business later needs more, larger storage can be offered as an expansion after the card, filesystem, and backup workflow are tested together.

Starting assumption: 32 GB card · around 2 GB reserved for apps · 20 GB advertised file space. Test actual formatted capacity and leave operating headroom before fixing the product numbers.

The current CrewBoard setup expects FAT32. Espressif documents FAT12/16/32 as the usual FAT support and says optional exFAT support is not enabled by default; its FAQ notes that cards over 32 GB commonly use exFAT. See Espressif FAT filesystem support and the Espressif FAT FAQ.

Opening and downloading documents

Each item in Document Share should respond naturally when clicked, with a separate download option available where useful.

The server can send a correct media type and choose whether a file is presented inline or as a download. The browser and device still decide what they can display and which desktop or mobile app, if any, can open a downloaded file.

Network name and configuration

Yes. The current CrewBoard setup already keeps the Wi-Fi network name and password in /config.json. It also supports an optional device hostname there, so a person can choose a memorable server name such as crewboard-cyd. On compatible clients, that can resolve as http://crewboard-cyd.local/; a DHCP reservation remains a useful fallback.

For a general server, the config could eventually include the business-server name, Wi-Fi details, and an initial administrator account. Keep passwords out of the on-screen status display, and make manual backup instructions explicit because copying the config also copies credentials.

The starter apps

Think of these as a small collection of apps, each doing one useful job. The first offer should be easy to explain to a landscaping crew or a family-run shop—not a smaller copy of all of SharePoint.

App 1

HomePage

The front door: links to the other apps, important notices, and a quick view of upcoming dates.

App 2

Employee Roster

Who works here and how to contact them. Includes individual employee logins plus administrator and owner accounts, with roles that control what each person can see or change.

App 3

Schedule

Track vacations and holidays first, then grow into the work schedule when the business is ready.

App 4

Document Share

A shared shelf for printable employee forms and business documents. For a paper-first shop, staff can print a direct-deposit form, fill it out on paper, and hand it in without putting personal information into the server.

Why this could fit: a family landscaping business or battery shop may not want a SharePoint system or online employee forms. A private place to check who is taking time off next week and print the right paper form can be useful on its own—and a gentle first step toward better organized business information later.

Possible future: installable apps and shared data

Instead of building every feature into one large website, the server could host separate app pages such as /roster, /customers, and /schedule. Each app would have its own screens and release, while using common sign-in and shared server services.

The app pages should use the server's API to access common data under /data. The browser cannot write files directly to the SD card; the server remains responsible for permissions, validation, and safe file updates. This also gives the server one place to keep shared records consistent when several apps use them.

What an installable app package might include

  • The app's web pages, styles, and browser-side code.
  • A manifest with a stable app ID, app version, supported server/API version range, required permissions, dependencies, and data-schema version.
  • Data definitions or starter files that the server can create when the app is installed.

Version dependencies deliberately

Use Semantic Versioning for app packages and the shared API: MAJOR.MINOR.PATCH. A major version signals an incompatible contract change; a minor version adds backward-compatible capability; a patch version fixes bugs without changing the contract. This only works if releases follow the rules consistently. See the Semantic Versioning specification.

Apps should declare a compatible range for each prerequisite instead of requiring one exact version forever. For example, Customers might accept Locations versions from 1.2.0 up to, but not including, 2.0.0. After installation, record the exact versions actually installed so the server can reproduce and diagnose that setup.

{
  "id": "customers",
  "version": "1.1.0",
  "requires": {
    "serverApi": ">=1.0.0 <2.0.0",
    "apps.locations": ">=1.2.0 <2.0.0"
  }
}
Example dependency: if /customers uses location records, the Customers package declares a compatible Locations prerequisite. The installer checks what is already installed and includes or offers a compatible prerequisite when it is missing.

Recommended installer rules

  • Keep the server API version separate from each app's version. Depend on stable API capabilities and data contracts, not private implementation details.
  • Keep dependencies one-way; reject circular dependencies. Check the entire dependency tree and all version constraints before changing the card.
  • Do not silently upgrade or replace a working prerequisite. Show the proposed changes and let the owner accept them.
  • Install only trusted packages and verify a vendor signature or trusted checksum. Do not let an app package execute arbitrary server-side code.
  • Create missing data files without overwriting existing business data. Record each data schema version separately from the app version.
  • Back up before a schema migration, apply a known migration path, and stop safely if it fails. Preserve business data when an app is removed unless the owner explicitly deletes it.
  • Store the installed app IDs, exact versions, dependency resolution, and package checksums in an installation record on the card.

This modular approach could support a basic server plus optional apps sold separately or in bundles. It is a future product idea, not part of the initial sales offer. A sensible first step would be to define the shared API and a small manifest format before building an app installer.

Design principles worth keeping

  • Local first: the main tools work on the business network without cloud services.
  • Simple permissions: explain who can view, upload, edit, and delete in plain language. Start with shared files; avoid personal folders.
  • Small and predictable: show upload limits, storage remaining if practical, and what happens when the card fills up.
  • Recoverable: power down, remove the card, and copy it to another device; document restore steps.
  • One job at a time: this is for a handful of users and ordinary office files, not simultaneous heavy uploads or a large company.
  • Private by network scope: the device is intended to be reached from the business network, not from the public internet, and accounts require passwords. Use “private” to describe local network access. Password protection helps control who can sign in, while HTTPS/TLS would encrypt traffic between a browser and the server.

Can we add encryption?

Yes, encryption can be part of the design. The most direct protection would be HTTPS/TLS, which encrypts browser traffic such as passwords and uploaded files while it travels over Wi-Fi. Espressif provides an HTTPS server component, but adding it to this Arduino-style server would take integration and memory testing. A locally generated certificate may also trigger a browser warning until each device trusts it. See Espressif HTTPS server documentation.

Encryption of the SD card itself is a separate choice. It could make the current “remove the card and copy it on a computer” backup approach harder, because a restore would need the right key and compatible software. For a starter product, password-protected accounts and a trusted, private business Wi-Fi are the simple baseline; HTTPS/TLS is a worthwhile security upgrade to investigate before making stronger claims.

Decisions for now

  • Storage: 32 GB card, about 2 GB reserved for apps, marketed as a 20 GB server.
  • Network: connect to the customer's existing router.
  • Files: shared documents, uploaded by the owner/admin and available for employees to download or print.
  • Privacy: local-network access with account passwords; investigate HTTPS/TLS as an encryption layer.

The examples that make the idea concrete are a small landscaping company and a family-run battery shop: both may be comfortable with paper, while still benefiting from knowing who is taking time off next week or having the right form ready to print.
