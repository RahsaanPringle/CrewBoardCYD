1. The short answer

Yes: CrewBoard could show a read-only PBI tab backed by a GitHub Project, with columns such as Backlog, Ready, In progress, In review, and Done. It could also display importance, effort, value, and links to the original issues.

Recommended starting direction: keep GitHub authoritative, show a small read-only board, and keep the GitHub token out of the browser. For local development, a server-side adapter is a natural experiment. For a CYD that must operate without a computer, evaluate a sanitized SD-card snapshot before committing to firmware-based GitHub access.

The biggest choice is not the card layout. It is which trusted component can hold a secret and fetch GitHub data. A companion server simplifies this, but changes the deployment requirements. A snapshot preserves standalone operation, but is not live.

Do not ask for a GitHub password. A PAT is itself a credential for API access; a username can identify the project owner, but a username/password pair is not needed alongside the token. Never ship a PAT in downloadable HTML, JavaScript, a static JSON settings file, or browser storage.

3. What credentials would be needed?

GitHub's Projects automation guide documents the GraphQL API and classic PAT scopes read:project for queries and project for mutations. This proposal starts read-only; it should not request write privileges merely to display cards. See the Projects API guide.

Project visibility and issue visibility are separate. Seeing a Project does not guarantee a token can read every private issue inside it. Organization policy, SSO authorization, membership, token approval, and repository permissions can all affect results. Test with the real target before writing the integration.

One integration identity versus each viewer's GitHub account

The simplest design has one administrator-configured integration identity. CrewBoard viewers use their existing CrewBoard login, not personal GitHub tokens. This needs a deliberate authorization decision: the integration owner's GitHub access must not automatically become every staff member's access.

  • Start owner-only unless the project is explicitly approved for crew-wide sharing.
  • Allowlist which project, repositories, fields, and items may be exposed.
  • Do not show private project titles, issue bodies, assignees, or metadata merely because the token can fetch them.
  • On disconnect or access revocation, stop refreshes and apply an explicit cache-removal policy; hiding the token alone does not remove previously cached private data.

A per-user GitHub sign-in model is possible but is a different product scope, involving delegated authorization, user/token lifecycle, and per-user caching. Avoid a PAT-entry form for every crew member.

5. Settings and secrets should not be the same file

Your idea of storing repository and Project information in settings is sound. Keep non-secret selection settings separate from the token whenever the chosen host permits it.

{
  "githubBoard": {
    "enabled": false,
    "ownerType": "user",
    "owner": "RahsaanPringle",
    "projectNumber": null,
    "repositoryFilter": ["RahsaanPringle/CrewBoardCYD"],
    "audience": "owner",
    "readOnly": true,
    "refreshSeconds": 300,
    "maxItems": 100,
    "fields": {
      "status": "Status",
      "effort": "Effort",
      "importance": "Importance",
      "value": "Value"
    }
  }
}

Illustrative schema only, not configuration accepted by CrewBoard today. A null Project number intentionally prevents enabling an unknown project. Field names are examples, not claims about the existing board. Resolve them to field IDs during validation; repository filtering needs an explicit rule for drafts.

If firmware must hold the token

An SD-root protected configuration is less exposed than a web asset, but it is still plaintext on removable storage and in backups. Reading a private file in firmware is not encryption. A CYD-only design should preferably provision the credential offline rather than accepting a GitHub PAT over the current HTTP interface. Evaluate physical access, rotation, backups, logs, and device compromise before approving it.

Token lifecycle

  • Use an expiring, least-privilege credential and document who owns rotation.
  • Show a clear expired/revoked/permission-denied state without printing the token.
  • Replacing a token must not reveal the old one; validate before switching the active connection.
  • Keep secret files and backups outside Git tracking. An ignore rule does not remove files already tracked.
  • If a real token reaches Git history or logs, revoke/rotate it first, then address retained copies. Deleting the visible file is not sufficient.
  • Restrict API destinations to the expected GitHub host; never accept an arbitrary fetch URL or follow a credential-bearing redirect to another origin.

6. How the board data would be fetched

A small adapter can locate a modern Project through user(login: ...).projectV2(number: ...) or the corresponding organization lookup. It can then read item content, selected custom-field values, and pagination information. Use query variables, not string concatenation of user-entered GraphQL.

query ProjectIdentity($owner: String!, $number: Int!) {
  user(login: $owner) {
    projectV2(number: $number) {
      id
      title
      url
    }
  }
}

This is a user-owned Project identity query, not the complete board implementation. An organization needs the organization root. A production query would also fetch the necessary item and field connections with explicit bounds and pageInfo { hasNextPage endCursor }.

  • A board can span repositories. Apply the repository filter deliberately; decide whether to exclude drafts or offer an explicit draft inclusion setting.
  • Decide whether pull requests, archived items, and Done items are included. An issue being closed is not necessarily the same as its Project Status being Done.
  • Field names can be renamed and option names differ between projects. Resolve IDs and report mapping errors rather than silently placing everything in Backlog.
  • Handle missing/redacted content without assuming it is a deleted issue or requesting broader access automatically.
  • Escape titles and metadata. If rich issue bodies are ever added, treat Markdown/HTML sanitization as a separate requirement.

7. Network failures, paging, and CYD limits

GitHub becomes an optional online dependency; CrewBoard's schedule, roster, messages, locations, and shared files must continue working without it. Do not contact GitHub during every normal CrewBoard request or block startup while waiting for it.

  • Bound work: use small pages, a maximum total item count, response-byte caps, timeouts, and a maximum number of pages per refresh. Paginate nested field connections too if necessary.
  • Report truncation: if the maximum is reached, show that only part of the board is displayed. Never imply that a partial list is complete.
  • Cache once: share refresh results on the trusted adapter instead of multiplying GitHub requests by every browser. Five-minute polling is a starting hypothesis, not a requirement.
  • Respect GitHub: inspect rate-limit headers, honor applicable retry instructions, and back off with jitter. Avoid automatic retry loops on invalid credentials.
  • Check GraphQL errors: an HTTP 200 response may still contain errors and partial data. Validate the response before replacing a known-good cache.
  • Keep stale state honest: last-known-good data may remain with a stale marker on network failure. Access revocation requires a stricter cache policy; do not retain private data indefinitely under an offline excuse.
  • Budget separately: existing CrewBoard collection limits do not automatically define a new board endpoint. Set an explicit snapshot/API size cap after measuring representative cards and ESP32 RAM use.
  • Verify HTTPS: never disable certificate verification to make firmware requests work. Plan certificate trust and clock initialization if the device makes TLS connections.

A disconnected browser, a CYD without internet, and an unavailable companion are different failures. Test them independently. A public GraphQL board is not inherently an offline board.

8. A sensible first release

Read-only PBI tab

  • One configured Project, with an explicit approved audience.
  • Compact list or horizontally navigable board, usable on phones and keyboards.
  • Title, Status, effort, importance, value, and source link.
  • Visible loading, empty, not configured, permission-denied, stale, and refresh-failed states.
  • Manual refresh plus a bounded background policy where the architecture permits it.
  • Owner-only connection management; staff never receive or replace the GitHub credential.
  • No GitHub writes. Users open GitHub to edit or complete items.

Deliberately defer

Drag-and-drop status changes, issue creation, comments, attachments, per-user GitHub sign-in, webhook hosting, and two-way synchronization of local Markdown checklists. They add write permissions, conflict handling, attribution, and substantially more failure modes.

Completion checkboxes need special care: viewing a board read-only cannot update GitHub. A future “mark complete” control would require a separately approved write feature and a defined mapping to Project Status, issue closure, or both. These actions are not equivalent.

How this relates to the existing backlog

The PBI roadmap can help choose which documents to turn into issues. The access-profile research should inform who can see private backlog content. The diagnostic console must not record tokens, authorization headers, private query variables, or issue content from this integration.

9. Decisions to make before coding

  1. Which Project? Record the exact URL, owner type, number, visibility, and whether it is the modern Projects experience.
  2. Who can see it? Owner only, selected access profiles, or all authenticated crew? Which private information is intentionally shared?
  3. How fresh? Is a periodically exported snapshot sufficient, or must the CYD display live updates without a companion?
  4. Where does the token live? Trusted host, exporter, or physically provisioned CYD? Who rotates/revokes it?
  5. Which items? This repository only or several; issues only or also PRs/drafts; include Done and archived items?
  6. Which fields? Confirm the real Status options and types for importance, effort, and value.
  7. What happens offline? Choose a stale-data policy, maximum cache age, and private-cache removal behavior.
  8. What is the source of truth? Prefer GitHub for board state; define how Markdown requirements are linked without pretending they synchronize.

Recommended follow-on research spike

Before a delivery PBI, validate a token from a trusted development process against the real Project. Produce a small sanitized sample payload, measure its size, test the selected owner/token combination, and choose live companion versus SD snapshot. This is a proposal for later work, not an instruction to paste a token into chat.

  • Document actual minimum permissions and owner-type compatibility.
  • Demonstrate field mapping and pagination with missing/draft/private items.
  • Compare deployment dependencies and resource costs for both viable architectures.
  • Specify allowed audience, safe configuration, cache policy, and token rotation.
  • Write a scoped implementation PBI only after those decisions are approved.
Bottom line: storing the Repo and Project selection is straightforward. Storing and using a PAT safely is the architectural decision. Start with a read-only board and keep the GitHub credential on the smallest trusted surface possible.
